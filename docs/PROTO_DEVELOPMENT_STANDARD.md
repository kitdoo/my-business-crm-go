# Protocol Buffers Development Standard

> **Version**: 1.0

This standard governs `.proto` files in this repository. It is the
wire-contract counterpart to [`SERVICE_DEVELOPMENT_STANDARD.md`](./SERVICE_DEVELOPMENT_STANDARD.md),
which defines how the Go service maps this contract onto entities, services,
storages, and transports.

Every example below uses a generic `Product` entity. The patterns apply to
any aggregate — substitute your entity's name wherever `Product` appears.

Codegen targets **Go** (server) and **JavaScript** (frontend) only — there
is no TypeScript, no Java, and no message-bus layer in this project.

## General Principles

### 1. Compatibility and versioning

- All changes must be backward compatible.
- New fields are added only as `optional`.
- Field removal is done through `reserved`, never by reusing a field number.
- A breaking change gets a new service version (`v1` → `v2`), not a field
  reshuffle inside `v1`.

### 2. Packages and organization

- **Types** (data models): `crm.types.{domain}` — e.g. `crm.types.product`.
- **Services** (RPC contracts): `crm.grpc.{domain}.v1` — e.g. `crm.grpc.product.v1`.

### 3. Language options

Only `go_package` is required in every file. JS clients are generated by a
buf plugin (`protoc-gen-es`, `target=js`) that derives module paths from the
proto package name — no per-file JS option is needed.

**`types/` directory — use the full module path:**
```proto
option go_package = "github.com/kitdoo/my-business-crm-go/proto/gen/go/types/{domain};{domain}pb";
```

**`services/` directory — use the short syntax:**
```proto
option go_package = ".;{service_name}pb";
```

**Examples:**
```proto
// types/product
option go_package = "github.com/kitdoo/my-business-crm-go/proto/gen/go/types/product;productpb";

// services/grpc/product/v1
option go_package = ".;productpb";
```

## File Structure

### Proto file template

```proto
syntax = "proto3";
package crm.types.{domain};

// 1. Standard Google protobuf (alphabetical)
import "google/protobuf/field_mask.proto";

// 2. Validation (services/ and types/*_create.proto, *_update.proto)
import "buf/validate/validate.proto";

// 3. Domain types, path relative to the proto/ module root (alphabetical)
import "types/brand/brand.proto";

option go_package = "github.com/kitdoo/my-business-crm-go/proto/gen/go/types/{domain};{domain}pb";

// File content
```

### Import order (strict)

1. Google protobuf imports (`google/protobuf/*`), alphabetical.
2. Buf validation (`buf/validate/*`).
3. Domain-specific imports, path relative to the `proto/` module root
   (`types/<domain>/<file>.proto`), alphabetical.

Groups are separated by an empty line.

`proto/` is a single buf module (see `proto/buf.yaml`) — every import path is
relative to that root, never a bare filename. `types/product/product.proto`
importing `types/common/common_localized_string.proto` writes the full path,
even though both live under `types/`.

### Dependency direction

Dependencies flow one way only: **`services/` → `types/<domain>/` → `types/common/`**.

- `types/common/` may only import other `types/common/` files and Google
  protobuf. It never imports a domain type or a service.
- `types/<domain>/` may import `types/common/` and other files in the same
  domain. It never imports another domain's types or a service.
- `services/` may import any `types/` file.

This keeps `types/common/` universally reusable and prevents circular
dependencies between domains.

### Validation import policy

`buf/validate/validate.proto` is allowed only in:
- `services/` (all files) — this includes Create/Update payload fields,
  which live directly on the request message (see
  [Message Patterns § Create/Update payloads](#2-createupdate-payloads-live-on-the-request)),
  and
- shared request-parameter types in `types/common/` that are never persisted
  and only ever appear embedded inside a request message (`Pagination`,
  `LocalizedString`) — these validate like any other request field.

A base entity type (`types/product/product.proto`, message `Product`)
carries no validation rules at all — `types/` never imports
`buf/validate/validate.proto` except for the `types/common/` exception above.

```proto
// ✅ services/grpc/product/v1/product_service.proto
message ProductCreateRequest {
  string sku = 1 [(buf.validate.field).required = true];
  // ...
}

// ❌ types/product/product.proto — base type, no validation
message Product {
  string sku = 1 [(buf.validate.field).string.min_len = 1]; // WRONG
}
```

## Basic Data Types

### 1. Timestamps

```proto
// Suffix "At" for a moment in time. Unix seconds — NEVER google.protobuf.Timestamp
// (see SERVICE_DEVELOPMENT_STANDARD.md § Timestamps for the entity-side codec).
int64 createdAt = 1;
int64 updatedAt = 2;
int64 deletedAt = 3;   // soft delete
```

```proto
// ❌ Do NOT use:
google.protobuf.Timestamp timestamp = 1; // wrong type
int64 date = 2;                          // ambiguous name
int64 lastUpdate = 3;                    // use updatedAt
```

### 2. Identifiers

```proto
message Product {
  // Unique identifier for the product.
  string id = 1 [(buf.validate.field).string.uuid = true];
}

message SaleItem {
  // Reference to the product being sold.
  string productId = 1 [(buf.validate.field).string.uuid = true];
}
```

- Own identifier: always `id`.
- Reference to another entity: `{entity}Id` (`productId`, `warehouseId`).

### 3. Financial amounts

**All monetary fields use `int64` in basis points (amount × 100). Never
`float`/`double`/`decimal`.**

```proto
// Unit price of the product.
// Value stored in basis points (amount * 100), e.g. 1050 = 10.50.
int64 priceAmount = 1 [(buf.validate.field).int64.gte = 0];
```

Naming: suffix `Amount` (`priceAmount`, `discountAmount`, `totalAmount`) —
never bare `price`/`cost`/`money`.

### 4. Percentage values

**All percentage fields use `int32`, plain integer percent (15 = 15%),
range-validated.**

```proto
// Commission percentage the partner receives on a sale.
// Value represents the percentage (e.g. 15 for 15%). Must be 0-100.
int32 commissionPercentage = 1 [
  (buf.validate.field).int32.gte = 0,
  (buf.validate.field).int32.lte = 100
];
```

For fractional percentages, store basis points of a percent (1550 = 15.50%)
and document the range as 0–10000.

### 5. Google protobuf types

**`FieldMask` is always `optional`:**
```proto
optional google.protobuf.FieldMask readMask = 1;
optional google.protobuf.FieldMask updateMask = 2;
```

**Validate with `buf.validate`, never a custom annotation:**
```proto
string name = 1 [(buf.validate.field).string.min_len = 1];
```

### 6. Entity tag (`etag`)

Every main entity message in `types/` carries an `etag` field **at position
101** for optimistic concurrency control:

```proto
message Product {
  string id = 1;
  // ... business fields (2-100) ...

  // Entity tag for optimistic concurrency control. Changes on every update.
  string etag = 101;
}
```

Position 101 leaves room for up to 100 business fields and keeps the etag's
location consistent across every entity in the codebase. Skip it on nested
non-primary messages, read-only references, and Request/Response messages.

## Naming Conventions

### 1. Message fields

- **Timestamps**: `createdAt`, `updatedAt`, `deletedAt`.
- **Identifiers**: `id` (own), `{entity}Id` (reference).
- **Special**: `etag` (field 101 on entities).
- **Names**: `name`, `description`, `title`.
- **Amounts/counts**: `{type}Amount` (money), `{type}Count` (counters).

### 2. Enums

```proto
enum ProductStatus {
  // Unspecified value. Do not use.
  PRODUCT_STATUS_UNSPECIFIED = 0;

  PRODUCT_STATUS_DRAFT = 1;
  PRODUCT_STATUS_ACTIVE = 2;
  PRODUCT_STATUS_INACTIVE = 3;
}
```

- Always include `{ENUM}_UNSPECIFIED = 0`, except `Sort` and `SortDirection`
  (below).
- Always use the full prefix (`PRODUCT_STATUS_ACTIVE`, not `STATUS_ACTIVE`).

**`Sort`/`SortDirection` exception** — no `UNSPECIFIED`, the default (0) is
the most common choice:

```proto
enum Sort {
  SORT_CREATED_AT = 0; // default
  SORT_UPDATED_AT = 1;
}

enum SortDirection {
  SORT_DIRECTION_ASC = 0;  // default — ascending
  SORT_DIRECTION_DESC = 1;
}
```

### 3. Messages

- Entity: `{EntityName}` (`Product`).
- Request/response: `{Method}{Entity}Request` / `Response`
  (`ProductCreateRequest`, `ProductCreateResponse`), or for list operations
  `{Entities}ListRequest` / `Response` (`ProductsListRequest`).
- Nested: `Options` (always field 99), `Filter`, `Sort`.

### 4. Formatting

- No blank line between fields within a message body (see
  [Message Patterns § Entity](#1-entity)).
- A blank line **may** separate logical groups of RPC methods within a
  service (e.g. plain CRUD vs. a documented special-purpose method) — this
  is a grouping device, not filler, so use it sparingly and only where the
  grouping itself is meaningful.
- No empty line right after `{` or right before `}`.
- RPC methods always end in `{}`, never `;` — even with no options:

```proto
// ✅
rpc Create (ProductCreateRequest) returns (ProductCreateResponse) {}

// ❌
rpc Create (ProductCreateRequest) returns (ProductCreateResponse);
```

## Message Patterns

### Reserved field numbers

- **99** — `optional Options options` on every request message.
- **101** — `etag` on every main entity message (see [above](#6-entity-tag-etag)).

### 1. Entity

Message bodies are compact — **no blank lines between fields**, in entity
types or in request/response messages. A blank line inside a message body
is a sign it's trying to be two messages; split it (a nested `message`, or
a separate top-level type) instead of using whitespace to fake structure.
Blank lines still separate one top-level message/enum from the next.

```proto
message Product {
  string id = 1;
  int64 createdAt = 2;
  int64 updatedAt = 3;
  optional int64 deletedAt = 4;
  string sku = 5;
  string name = 6;
  string description = 7;
  string brandId = 8;
  ProductStatus status = 9;
  string etag = 101;
}
```

### 2. Create/Update payloads live on the request

There is **no `types/<domain>/<entity>_create.proto` or `*_update.proto`**.
Create/Update fields are declared directly on `{Entity}CreateRequest` /
`{Entity}UpdateRequest` in `services/` — a create/update payload is a request
shape, not a persisted type, and doesn't need a `types/` file of its own.

- `{Entity}CreateRequest` fields sit next to `Options options = 99`. Required
  fields carry `(buf.validate.field).required = true`.
- `{Entity}UpdateRequest` fields are **all `optional`** (partial updates),
  alongside the required `id` and `Options options = 99`.

```proto
// services/grpc/product/v1/product_service.proto
message ProductCreateRequest {
  message Options {
    optional google.protobuf.FieldMask readMask = 1;
  }

  string sku = 1 [(buf.validate.field).required = true];
  string name = 2 [(buf.validate.field).required = true];
  string brandId = 3 [(buf.validate.field).required = true, (buf.validate.field).string.uuid = true];

  optional Options options = 99;
}

message ProductUpdateRequest {
  message Options {
    optional google.protobuf.FieldMask updateMask = 1;
    optional string etag = 2;
  }

  string id = 1 [(buf.validate.field).required = true, (buf.validate.field).string.uuid = true];

  optional string name = 2;
  optional string description = 3;

  optional Options options = 99;
}
```

This keeps every generated Go/JS client type for a domain in one file pair
(`types/<domain>/<entity>.proto` for the persisted shape,
`services/grpc/<domain>/v1/<entity>_service.proto` for every request/response)
instead of three, and avoids a redundant nested `product.ProductCreate` field
that duplicates the request message's own identity.

### 3. Get request

```proto
message ProductGetRequest {
  message Options {
    optional google.protobuf.FieldMask readMask = 1;
  }
  string id = 1 [(buf.validate.field).required = true, (buf.validate.field).string.uuid = true];
  optional Options options = 99;
}

message ProductGetResponse {
  crm.types.product.Product product = 1;
}
```

### 4. List request

List requests separate **scope** (which parent/boundary the request is
limited to — only add this if the domain has one) from **filter** (which
items within that scope to return, always optional, always the caller's
preference):

```proto
message ProductsListRequest {
  // Omit for all brands.
  optional string brandId = 1 [(buf.validate.field).string.uuid = true];
  message Sort {
    enum Field {
      FIELD_CREATED_AT = 0;
      FIELD_NAME = 1;
    }
    Field field = 1 [(buf.validate.field).enum.defined_only = true];
    crm.types.common.SortDirection direction = 2;
  }
  optional Sort sort = 2;
  optional crm.types.common.Pagination pagination = 3;
  message Filter {
    repeated ProductStatus statuses = 1 [(buf.validate.field).repeated.unique = true];
    // Document which entity fields this matches.
    optional string searchQuery = 2 [(buf.validate.field).string.max_len = 255];
    repeated string categoryIds = 3 [(buf.validate.field).repeated.items.string.uuid = true];
    optional crm.types.common.PeriodFilter createdAt = 4;
  }
  optional Filter filter = 4;
  message Options {
    optional google.protobuf.FieldMask readMask = 1;
    bool includeTotalCount = 2;
  }
  optional Options options = 99;
}

message ProductsListResponse {
  repeated crm.types.product.Product items = 1;
  // Populated only if includeTotalCount=true.
  optional int64 total = 2;
  // Empty when there are no more results.
  optional string nextCursor = 3;
}
```

Every List `Filter` should exhaust the entity's realistic selection criteria
— enum status/type fields, a free-text search over the fields users actually
search by, ID-list multi-select for every relation the entity carries
(`categoryIds`, `createdBy`, ...), and a `PeriodFilter` on every timestamp
worth filtering by (usually `createdAt`). **Min/max range pairs are for
dates and counts only** (`PeriodFilter`, a stock quantity) — money and
percentage fields don't get one; nobody filters a product list by "price
between X and Y basis points" in practice, and if the domain ever needs it,
add it then. Don't add a filter that's always true for every row the entity
can have (e.g. "has at least one sale" on a `Client` that's only ever
created *from* a sale) — it isn't a selection criterion.

Shared `SortDirection` and `Pagination` types live in `types/common/`:

```proto
// types/common/common_sort_direction.proto
enum SortDirection {
  SORT_DIRECTION_ASC = 0;
  SORT_DIRECTION_DESC = 1;
}

// types/common/common_pagination.proto
message Pagination {
  int64 limit = 1 [(buf.validate.field).int64.gte = 1, (buf.validate.field).int64.lte = 1000];
  optional string cursor = 2;
}
```

### 5. Create request

```proto
message ProductCreateRequest {
  message Options {
    optional google.protobuf.FieldMask readMask = 1;
  }
  string sku = 1 [(buf.validate.field).required = true];
  string name = 2 [(buf.validate.field).required = true];
  string brandId = 3 [(buf.validate.field).required = true, (buf.validate.field).string.uuid = true];
  optional Options options = 99;
}

message ProductCreateResponse {
  crm.types.product.Product product = 1;
}
```

> Idempotency keys travel via the `Idempotency-Key` HTTP header or gRPC
> metadata — never as a request field.

### 6. Update request

```proto
message ProductUpdateRequest {
  message Options {
    // Make etag required + non-optional when strict concurrency control
    // matters more than caller convenience.
    optional google.protobuf.FieldMask updateMask = 1;
    optional string etag = 2;
  }
  string id = 1 [(buf.validate.field).required = true, (buf.validate.field).string.uuid = true];
  optional string name = 2;
  optional string description = 3;
  optional Options options = 99;
}

message ProductUpdateResponse {
  crm.types.product.Product product = 1;
}
```

**A status field moves to a dedicated RPC only when the transition has real
rules of its own** — validation, side effects, or a multi-state lifecycle
described in the spec (e.g. a `Sale` moving draft → paid → shipped →
completed, or a `Warehouse` deactivation that must check stock is zero
first). Don't invent `Activate`/`Deactivate` for every enum with an
active/inactive value — if the spec gives the entity nothing but plain
`Create`/`Update` and a two-value status, the status is just another
`Update` field:

```proto
// ✅ CORRECT — no described transition logic, status is a plain field
message ProductUpdateRequest {
  optional ProductStatus status = 8;
}

// ✅ CORRECT — Sale.Status has a real lifecycle with distinct rules per
// transition (see the spec), so it gets dedicated RPCs instead
service SalesService {
  rpc UpdateStatus (SaleUpdateStatusRequest) returns (SaleUpdateStatusResponse) {}
  rpc Cancel (SaleCancelRequest) returns (SaleCancelResponse) {}
}
```

**Field behavior** — annotate an `Update` field with `google.api.field_behavior`
only when the default ("can be updated or cleared via `updateMask`") isn't
right:

| Annotation      | Meaning |
|-----------------|---------|
| *(none)*        | Default — updatable, clearable |
| `REQUIRED` | If present in `updateMask`, must be set — cannot be cleared |
| `IMMUTABLE` | Cannot change after creation — error if present in `updateMask` |
| `OUTPUT_ONLY` | Server-computed — silently dropped from `updateMask` |

```proto
import "google/api/field_behavior.proto";

optional string sku = 5 [(google.api.field_behavior) = IMMUTABLE];
```

### 7. Delete request

```proto
message ProductDeleteRequest {
  message Options {
    optional string etag = 1;
  }
  string id = 1 [(buf.validate.field).required = true, (buf.validate.field).string.uuid = true];
  optional Options options = 99;
}

message ProductDeleteResponse {}
```

Delete is always a soft delete server-side — see
[`SERVICE_DEVELOPMENT_STANDARD.md` § All deletes are soft](./SERVICE_DEVELOPMENT_STANDARD.md).
The wire contract has no separate "hard delete" method.

## gRPC Services

### Method naming

```proto
service ProductsService {
  rpc Create (ProductCreateRequest) returns (ProductCreateResponse) {}
  rpc Get (ProductGetRequest) returns (ProductGetResponse) {}
  rpc Update (ProductUpdateRequest) returns (ProductUpdateResponse) {}
  rpc Delete (ProductDeleteRequest) returns (ProductDeleteResponse) {}
  rpc List (ProductsListRequest) returns (ProductsListResponse) {}
}
```

Prefer bare `Create`/`Get`/`Update`/`Delete`/`List` over `CreateProduct` —
the service name already carries the entity.

### Documentation

Keep RPC and message documentation to what a caller needs — 1–3 lines, no
exhaustive gRPC status-code enumeration (that duplicates what `MapError`
already encodes server-side and rots the moment an error mapping changes):

```proto
// ✅ CORRECT
// Creates a new product and returns it with its assigned id and timestamps.
rpc Create (ProductCreateRequest) returns (ProductCreateResponse) {}

// ❌ WRONG — restates the obvious, enumerates status codes that belong in code review, not the contract
// Creates a new product.
//
// Errors:
// - INVALID_ARGUMENT (3): missing required fields
// - ALREADY_EXISTS (6): sku already exists
// - INTERNAL (13): database error
rpc Create (ProductCreateRequest) returns (ProductCreateResponse) {}
```

## Data Validation

### Where validation lives

- `services/` — every request message is validated.
- `types/` — only `*Create`/`*Update` messages. Base types (`Product`) carry
  no validation.

### `required` is not validation

`(buf.validate.field).required = true` only says the field must be present —
it does not check the value is well-formed. **A field with a real, universal
shape (email, UUID, a bounded number) gets a rule for that shape, always,
required or not.** "I'll validate it in the handler" is not an answer here;
if protovalidate can express the constraint, it belongs on the field. This
cuts both ways: don't invent a shape a field doesn't actually have —
`phone` has no single valid pattern across countries, so it gets a length
bound and nothing else (see [Built-in validators](#built-in-validators)).

```proto
// ❌ WRONG — required says nothing about what a valid email looks like
string email = 1 [(buf.validate.field).required = true];

// ✅ CORRECT
string email = 1 [(buf.validate.field).required = true, (buf.validate.field).string.email = true];

// ✅ CORRECT — same rule applies to optional fields; presence and shape are independent
optional string email = 1 [(buf.validate.field).string.email = true];
```

### Built-in validators

```proto
// Required field
string name = 1 [(buf.validate.field).required = true];

// UUID — every id / {entity}Id field, everywhere it appears (Create,
// Update, Filter, List scope), not only where it happens to be required
string id = 1 [(buf.validate.field).string.uuid = true];

// Email — protovalidate's built-in RFC check, not a hand-rolled regex
string email = 1 [(buf.validate.field).string.email = true];

// Phone — no format/pattern. Numbering plans vary too much by country
// (length, leading 0 vs +, area codes, extensions) for a single regex to
// be correct; a bound guards against abuse, nothing more.
string phone = 1 [(buf.validate.field).string.max_len = 32];

// String length
string sku = 1 [(buf.validate.field).string.min_len = 1, (buf.validate.field).string.max_len = 64];

// Numeric range
int32 percentage = 1 [(buf.validate.field).int32.gte = 0, (buf.validate.field).int32.lte = 100];

// Enum — reject unknown/future values the client didn't mean to send
crm.types.product.ProductStatus status = 1 [(buf.validate.field).enum.defined_only = true];

// oneof — exactly one branch required
oneof payment_method {
  option (buf.validate.oneof).required = true;
  string bankAccount = 1;
  string cardNumber = 2;
}
```

For anything else domain-specific, prefer a CEL predicate over duplicating
ad-hoc regex across files — see
[buf.build/bufbuild/protovalidate](https://buf.build/bufbuild/protovalidate)
for the CEL expression syntax.

## Documentation

**Really minimal.** Most fields need zero comment — the name, type, and
`buf.validate` rule already say what a field is and whether it's required.
A comment earns its place only for what the declaration can't say: wire
encoding (basis points, Unix seconds, ISO codes), a non-obvious invariant,
or why a field is absent. Never restate the field/message name, never add
"Required."/"Optional." (the type already says that), never narrate the
obvious.

**Never describe server-side behavior.** A `.proto` comment documents the
wire contract — what a field/message/RPC *is*, not what the service *does*
with it. Validation rules, config-driven defaults, bootstrap procedures,
token expiry policy, when a delete gets rejected — all of that lives in
`SERVICE_DEVELOPMENT_STANDARD.md`-governed Go code, or nowhere in the
comment at all if it's not decided yet. A proto comment that could go stale
without anyone touching the `.proto` file is in the wrong place.

```proto
// ✅ — encodes something the declaration can't
// Basis points (amount * 100).
int64 priceAmount = 6;

// ❌ — the declaration already says this
// The unique identifier for the product.
string id = 1;

// ✅ — states real intent in one line
// Carries no price or stock — those live in ProductPrice and Inventory.
message Product {

// ❌ — restates the type name
// Represents the Product model. Product message definition.
message Product {

// ❌ — server-side bootstrap procedure, not a wire-contract fact; also the
// kind of comment nobody remembers to update when the procedure changes
// Bootstrap admin is created from config, not through this request.
message UserCreateRequest {

// ❌ — describes internal token-issuance policy, and it's wrong on top of
// it (the actual expiry lives in service config) — this couldn't have
// drifted if it had never been written into the proto
// Non-expiring; valid until logout or manual invalidation.
string token = 1;
```

Enum values: a comment only on the values that need one (an exception, a
non-obvious ordering), never a blanket comment on every value.

```proto
enum MovementType {
  MOVEMENT_TYPE_UNSPECIFIED = 0;
  MOVEMENT_TYPE_RECEIPT = 1;
  MOVEMENT_TYPE_SALE = 2;
  MOVEMENT_TYPE_WRITE_OFF = 3;
  MOVEMENT_TYPE_ADJUSTMENT = 4;
  // Warehouse-to-warehouse; recorded as a paired debit/credit movement.
  MOVEMENT_TYPE_TRANSFER = 5;
}
```

## Templates

### New entity (types/)

```proto
// product/product.proto
syntax = "proto3";
package crm.types.product;

option go_package = "github.com/kitdoo/my-business-crm-go/proto/gen/go/types/product;productpb";

message Product {
  string id = 1;
  int64 createdAt = 2;
  int64 updatedAt = 3;
  optional int64 deletedAt = 4;
  string sku = 5;
  string name = 6;
  ProductStatus status = 7;
  string etag = 101;
}

enum ProductStatus {
  PRODUCT_STATUS_UNSPECIFIED = 0;
  PRODUCT_STATUS_DRAFT = 1;
  PRODUCT_STATUS_ACTIVE = 2;
  PRODUCT_STATUS_INACTIVE = 3;
}
```

That's the only file under `types/product/` — no `product_create.proto` /
`product_update.proto`. Create/Update fields go straight on the request
message in the service file (see
[Message Patterns § Create/Update payloads](#2-createupdate-payloads-live-on-the-request)).

### gRPC service (services/)

```proto
syntax = "proto3";
package crm.grpc.product.v1;

import "google/protobuf/field_mask.proto";
import "buf/validate/validate.proto";
import "types/product/product.proto";

option go_package = ".;productpb";

service ProductsService {
  rpc Create (ProductCreateRequest) returns (ProductCreateResponse) {}
  rpc Get (ProductGetRequest) returns (ProductGetResponse) {}
  rpc Update (ProductUpdateRequest) returns (ProductUpdateResponse) {}
  rpc Delete (ProductDeleteRequest) returns (ProductDeleteResponse) {}
  rpc List (ProductsListRequest) returns (ProductsListResponse) {}
}

message ProductCreateRequest {
  message Options {
```

## Common Patterns

### Optional references

A reference that may be absent is `optional {entity}Id`, not an empty-string
sentinel:

```proto
// ✅
optional string brandId = 1 [(buf.validate.field).string.uuid = true];

// ❌ — "" as "no brand" is an implicit, undocumented convention
string brandId = 1;
```

### Soft delete on the wire

`Delete` never removes data server-side — see
[`SERVICE_DEVELOPMENT_STANDARD.md`](./SERVICE_DEVELOPMENT_STANDARD.md). The
proto contract reflects this: `deletedAt` is a plain field on the entity (set
once, never unset), and there is no `Restore`/`Undelete` RPC unless the
domain explicitly needs one.

### Versioning a breaking change

Add a new service (`crm.grpc.product.v2`) rather than reshaping `v1` in
place. `v1` keeps serving existing callers until they migrate.

## Generation

`proto/` is a self-contained buf workspace — `buf.yaml` (the module + lint
config), `buf.lock` (pinned `buf.build/bufbuild/protovalidate` dependency),
and one `buf.gen.<language>.yaml` per codegen target. The **root**
`Makefile` drives it (`##@ Proto` section) — there is no separate
`proto/Makefile`, so codegen is one `make` away from the repo root like
everything else. Generated code is never committed — `proto/.gitignore`
excludes `gen/`.

```
proto/
├── buf.yaml
├── buf.lock
├── buf.gen.go.yaml  # protoc-gen-go + protoc-gen-go-grpc
├── buf.gen.js.yaml  # protoc-gen-es, target=js
├── types/
├── services/
└── gen/                # generated, gitignored
    ├── go/             # mirrors types/ and services/, paths=source_relative
    └── js/
```

```bash
# from the repo root
make devtools    # includes protoc-gen-go, protoc-gen-go-grpc
make proto-go    # -> proto/gen/go/...
make proto-js    # -> proto/gen/js/... (needs `npm i -g @bufbuild/protoc-gen-es`)
make proto       # both
make proto-lint / make proto-build
```

`make proto-js` sets `NODE_OPTIONS=--no-experimental-webstorage` — newer
Node runtimes ship an experimental global `localStorage` stub that crashes
`protoc-gen-es`'s TS-inference dependency (`@typescript/vfs`) even though
this project only generates plain `.js`, never `.ts`.

A new target language gets its own `buf.gen.<language>.yaml` and a
`proto-<language>` target in the root `Makefile` — never a shared,
multi-plugin file. Each plugin only needs to know its own output directory
and options.

## Review Checklist

### ✅ File structure
- [ ] `go_package` set; `types/` uses the full module path, `services/` uses `.;{name}pb`.
- [ ] Imports grouped and alphabetized: protobuf → buf validate → domain.
- [ ] `types/common/` imports nothing outside `types/common/`.

### ✅ Naming
- [ ] Timestamps: `createdAt`/`updatedAt`/`deletedAt`, `int64` Unix seconds.
- [ ] `deletedAt` present on every entity except one with a documented reason
  to skip it (e.g. an append-only ledger like `InventoryMovement`).
- [ ] IDs: `id` (own), `{entity}Id` (reference), UUID-validated in `services/`.
- [ ] Enums: full-prefixed, `_UNSPECIFIED = 0` (except `Sort`/`SortDirection`).

### ✅ Data types
- [ ] Money: `int64` basis points, `{type}Amount` suffix.
- [ ] Percentages: `int32`, 0–100 range validated.
- [ ] No `google.protobuf.Timestamp` anywhere.

### ✅ Message patterns
- [ ] `Options options = 99` on every request; `etag = 101` on every entity.
- [ ] `CreateRequest` fields validate required fields directly (no `types/*_create.proto`); `UpdateRequest` fields are all-optional (no `types/*_update.proto`).
- [ ] `status` is a dedicated RPC only where the spec describes real transition rules for it — otherwise it's a plain `*UpdateRequest` field.
- [ ] No `allowMissing` on `Delete` — deleting an absent id is `NOT_FOUND`.
- [ ] List requests separate scope (root-level) from filter (`Filter` message).

### ✅ Validation
- [ ] `buf.validate` only in `services/` request messages and the `types/common/` request-parameter exception (`Pagination`, `LocalizedString`).
- [ ] Base entity types in `types/<domain>/` carry no validation rules at all.
- [ ] `required` is never the only rule on a field with a real shape — email gets `string.email`, every `id`/`{entity}Id` gets `string.uuid`, every enum gets `enum.defined_only`, bounded numbers get a range — in Create, Update, and Filter alike. Fields with no universal shape (`phone`) get a length bound, not an invented pattern.

### ✅ Documentation
- [ ] No blank lines between fields in a message body.
- [ ] Every comment says something the declaration can't; no restated names,
  no "Required."/"Optional." prefixes, no exhaustive error-code lists.
- [ ] No comment describes server-side behavior (bootstrap procedures,
  config-driven defaults, when a delete gets rejected, token policy, ...) —
  that belongs in Go code, not in the wire contract.

### ✅ Compatibility
- [ ] New fields are `optional`, never renumbering an existing field.
- [ ] Breaking changes land in a new service version, not in place.

## Conclusion

This standard keeps the proto surface small and predictable:

1. **One entity, one file** — `types/<domain>/<entity>.proto` holds the
   persisted shape only; Create/Update payloads live on the request message
   in `services/`, generated for Go and JavaScript only.
2. **Fixed field numbers** — `options = 99`, `etag = 101` — so tooling and
   reviewers never have to guess.
3. **Unix-second timestamps, basis-point money, integer percentages** — no
   floating point, no ambiguous units.
4. **Soft delete only** — no field or method on the wire implies a hard
   delete exists.
5. **Status is a plain `Update` field unless the spec describes real
   transition rules for it** — a dedicated RPC is earned, not assumed.
6. **No blank lines, no comment that doesn't earn its place** — the proto
   surface should read like a schema, not prose.

When writing or reviewing `.proto` files, follow this standard strictly.
