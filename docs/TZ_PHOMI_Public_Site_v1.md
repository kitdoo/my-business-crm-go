# ТЗ — PHOMI Srbija: Публичный сайт (Frontend)

> Версия: 1.0. Публичный маркетинговый сайт + базовый каталог товаров, читающий данные из того же бэкенда, что и админ-панель (см. `TZ_MyBusiness_CRM_Web_Admin_v1.2.md`). Архитектурные принципы (BFF, i18n, design tokens, единые UI-компоненты) — сквозные с админкой, чтобы не изобретать два разных подхода в одном проекте.
>
> **Изменения в 1.1** (по факту реализации): вопреки §8.1 ниже («без корзины, без оформления заказа»), в проекте появилась корзина (`app/composables/useCart.js`, `app/components/cart/CartDrawer.vue`) — решение расширить базовый каталог до сценария «собрать список интересующих товаров и отправить одной заявкой» принято уже в ходе реализации. §8.1/§8.5 ниже описывают исходный, более узкий scope; фактическое поведение корзины (что именно она отправляет — заявку с позициями через форму «Стать дилером»/«Контакт», или отдельный эндпоинт) не задокументировано отдельно и требует сверки с кодом при следующей правке.

## 0. Контекст и границы

Это **отдельное Nuxt-приложение** (или отдельный layout/группа роутов в том же монорепо — на усмотрение реализации, см. п.1.3), обслуживающее анонимных посетителей сайта. Оно **не путает** зоны ответственности с админ-панелью:

- Публичный сайт — **только чтение** данных каталога (товары со статусом `Active`) + приём заявок (форма «Стать дилером», форма «Контакт»). Никакого CRUD, никакого RBAC на посетителя.
- Управление каталогом (создание/редактирование товаров, брендов, категорий, статусов) происходит **исключительно через админ-панель** (см. существующее ТЗ), это уже реализовано и не переделывается.
- Единственная точка пересечения с админкой на этом сайте — **иконка входа в админку** в шапке/подвале (просто ссылка, см. п.4.5), без встраивания самой админки внутрь публичного сайта.

## 1. Стек и ключевые архитектурные решения

| Слой | Выбор | Почему |
|---|---|---|
| Фреймворк | **Nuxt 3** (Vue 3, Composition API, `<script setup>`) | SSR обязателен для публичного сайта — SEO, скорость первой отрисовки, соцпревью (og:image/og:title на каждой странице товара) |
| Язык | **JavaScript** + JSDoc на публичных composables | Единообразие с админ-панелью, тот же стек |
| UI-библиотека | **`@nuxt/ui` (Nuxt UI v3, Tailwind)** | Тот же кит, что в админке — переиспользуем токены дизайна (п.5) и часть общих компонентов (StatusBadge, MoneyLabel, LocalizedText) |
| Состояние | **Pinia** | Нужен минимально — язык интерфейса, корзина/список избранного не предусмотрены на этом этапе |
| Валидация форм | **Zod** | Формы «Стать дилером» и «Контакт» — валидация телефона/email/обязательных полей |
| i18n | **`@nuxtjs/i18n`** | Три языка: `sr` (обязательный/дефолтный), `en`, `ru` — см. п.6 |
| Иконки | **`@iconify-json/lucide`** | Согласовано с админкой |
| Данные каталога | **Только чтение**, через тонкий BFF-слой (`server/api/**`) к тому же бэкенду, что и админка — **без токена**, т.к. каталог публичен (см. п.2) | Не плодить два разных бэкенда под один каталог |

### 1.1 Откуда берутся данные каталога

Публичный каталог читает те же сущности, что определены в бэкенд-ТЗ CRM: `Product` (+ `ProductPrice`, `Brand`, `Category` для фильтров и лейблов) и `Client`-заявки создаются через `PartnersService`/`ClientsService`-подобный поток (см. п.7 — форма «Стать дилером» создаёт запись `Partner`/лид, форма «Контакт» — просто письмо, без записи в CRM, если явно не согласовано иначе).

**Важно:** для публичного сайта нужен **отдельный, публичный, урезанный** RPC-доступ (или HTTP-эндпоинт) к списку товаров — тот же `ProductsService.List`, но:
- вызывается **без авторизационного токена** (или со служебным read-only токеном, зашитым только на сервере Nitro — никогда не отдаётся браузеру);
- фильтруется на уровне BFF так, чтобы отдавались **только** товары со статусом `Active` — не полагаться на то, что бэкенд сам это фильтрует по умолчанию, фильтр `statuses: [ACTIVE]` **всегда** прописан в запросе явно на сервере Nuxt;
- отдаёт только поля, нужные каталогу (`id, sku, name, imageIds, price, status`) — не весь объект `Product` (без служебных полей вроде `createdBy`, аудита и т.п., если бэкенд их возвращает).

### 1.2 RPC-транспорт

Идентично п.1.1 админ-ТЗ: gRPC-клиент (`@grpc/grpc-js`) живёт **только** в `server/api/**` (Nitro/Node), браузер никогда не обращается к gRPC напрямую. Деплой — Node.js server runtime, не edge/serverless (см. ограничение в админ-ТЗ, действует и здесь).

### 1.3 Один проект или два

**[best practice]** Рекомендуется **отдельный Nuxt-проект** от админки (не общий layout в одном приложении):
- разные аудитории (анонимные посетители vs. авторизованные сотрудники) → разные требования к SSR/SEO/кэшированию;
- разные деплой-профили (публичный сайт — за CDN с агрессивным кэшем статики, админка — нет);
- проще держать бандл публичного сайта маленьким (не тащить Pinia-стор с RBAC, EntityRegistry на 11 сущностей и т.д., которые сайту не нужны).

Общий код (design tokens, форматтеры денег/дат, возможно часть Zod-схем) — выносится в **общий npm-пакет/workspace** (`packages/shared` в монорепо), переиспользуется обоими проектами, а не копипастится.

## 2. Аутентификация — её почти нет

На публичном сайте **нет** пользовательских аккаунтов, логина, сессий для посетителей. Единственный автоматический вызов бэкенда с намёком на «авторизацию» — служебный read-only токен для чтения каталога (см. п.1.1), который:
- хранится только в `runtimeConfig.grpc` на сервере (env-переменная, никогда не в клиентском бандле);
- используется исключительно в `server/api/catalog/**`;
- не имеет отношения к пользовательским токенам админки — это отдельная, максимально урезанная по правам read-only учётная запись на бэкенде (или отдельный публичный незащищённый RPC-метод, если бэкенд-команда решит завести такой явно для публичного каталога — уточнить с бэкенд-ТЗ при реализации, т.к. в текущем `internal/rbac` этого разделения может не быть и потребуется отдельное решение бэкенда).

## 3. Конфигурация — runtime, не хардкод

Аналогично п.3 админ-ТЗ:

```js
// nuxt.config.js
export default defineNuxtConfig({
  runtimeConfig: {
    grpc: {
      baseUrl: '',          // env: NUXT_GRPC_BASE_URL
      readOnlyToken: '',    // env: NUXT_GRPC_READONLY_TOKEN — служебный токен для чтения каталога, см. п.2
      timeoutMs: 15000,
    },
    images: {
      baseUrl: '',           // env: NUXT_IMAGES_BASE_URL — тот же HTTP-хост картинок, что в админке
    },
    mail: {
      // для форм «Стать дилером» / «Контакт», см. п.7
      smtpUrl: '',            // env: NUXT_MAIL_SMTP_URL, либо адрес транзакционного email-провайдера
      contactRecipient: '',   // env: NUXT_MAIL_CONTACT_RECIPIENT
    },
    public: {
      appName: 'PHOMI Srbija',
      defaultLocale: 'sr',
      supportedLocales: ['sr', 'en', 'ru'],
      adminUrl: '',            // env: NUXT_PUBLIC_ADMIN_URL — куда ведёт иконка входа в админку, см. п.4.5
    },
  },
})
```

Один и тот же собранный образ конфигурируется под dev/stage/prod переменными окружения — без пересборки, как в админке.

## 4. Layout и навигация

### 4.1 Шапка (TopBar)

```
┌──────────────────────────────────────────────────────────────────────┐
│ [Лого PHOMI SRBIJA]     KATALOG  POSTANI DILER  ZAVRŠENI PROJEKTI  KONTAKT   🌐 sr/en/ru   🔒 │
└──────────────────────────────────────────────────────────────────────┘
```

- Фон — прозрачный/светлый поверх hero-изображения на главной (см. скриншоты), становится сплошным белым или тёмно-серым при скролле (`sticky` + смена фона по `scrollY`, простой composable `useScrollHeader()`).
- Пункты меню — **ровно 4**, плоский список, никаких выпадающих подменю (тот же принцип «без промежуточного клика по разделу», что в SideMenu админки, п.8.2 админ-ТЗ):
  - `KATALOG` → `/katalog`
  - `POSTANI DILER` → `/postani-diler` (или якорь на секцию, если решено оставить как one-page блок — см. п.4.1a)
  - `ZAVRŠENI PROJEKTI` → `/projekti`
  - `KONTAKT` → `/kontakt`
- Активный пункт подсвечивается бирюзовым (`tokens.color.brand[500]`), как активный пункт в SideMenu админки.
- Переключатель языка — идентичный паттерн из п.8.1 админ-ТЗ (`@nuxtjs/i18n`, `sr/en/ru`, код языка текстом, не флаг конкретной страны).
- На `< lg` — гамбургер, открывающий меню overlay на весь экран (тёмный фон `#333333`, крупные пункты, см. брейкпоинты п.8).

**4.1a Важное архитектурное решение:** судя по скриншотам, часть контента (`POSTANI PARTNER`, «PHOMI U SVETU», «KLJUČNE PREDNOSTI», «PRIMERI IZVEDENIH PROJEKATA») сейчас живёт **одной длинной главной страницей** (one-page с якорями). Пункты меню `POSTANI DILER` и `ZAVRŠENI PROJEKTI` при этом могут либо:
- (A) вести на **отдельные страницы** `/postani-diler` и `/projekti` с полноценным контентом и собственным SEO (title/description/og) — **рекомендуется [best practice]**, лучше для SEO и для будущего расширения (напр. фильтр проектов по стране/типу объекта);
- (B) быть якорями (`#postani-diler`, `#projekti`) на главной, если контент решено оставить компактным.

Зафиксировать решение с заказчиком до начала вёрстки — от этого зависит структура роутов и `sitemap.xml`. Ниже ТЗ описывает по варианту (A), как более гибкому и SEO-дружественному; при выборе (B) секции переиспользуются как компоненты, вставленные на `/` вместо отдельных страниц.

### 4.2 Иконка входа в админку

Требование заказчика — **иконка** (не текстовая ссылка) для входа в панель управления. Реализация:

```vue
<!-- app/components/layout/AdminLoginLink.vue -->
<a
  :href="adminUrl"
  target="_blank"
  rel="noopener"
  class="..."
  :aria-label="$t('nav.adminLogin')"
>
  <UIcon name="i-lucide-lock" />
</a>
```

- `adminUrl` — из `runtimeConfig.public.adminUrl` (см. п.3), т.е. адрес отдельно задеплоенной админ-панели (см. п.1.3) — **не** роут внутри этого проекта.
- Позиция — в TopBar, крайний правый элемент после переключателя языка (некликбейтная, малозаметная иконка — замок или шестерёнка, `i-lucide-lock` / `i-lucide-settings`, финальный выбор — на усмотрение дизайнера при вёрстке).
- Открывается в новой вкладке (`target="_blank"`), т.к. это переход в другое приложение, не внутренняя навигация.
- **[best practice]** Продублировать эту же иконку/ссылку в футере (мелким текстом «Admin» рядом с копирайтом) — стандартная практика для B2B-сайтов, не мешает основным посетителям.

## 5. Дизайн-система

**Переиспользуется файл токенов из админ-панели** (`tokens.js`, п.7 админ-ТЗ) — тот же бирюзовый `#85C5CF`, тот же тёмно-серый `#333333`, та же палитра статусов для `StatusBadge` (см. п.8.3). Если проекты — раздельные репозитории (п.1.3), токены выносятся в общий пакет `packages/shared/design/tokens.js`, импортируются в оба.

**Отличия публичного сайта от админки** (по скриншотам):
- Здесь **допустима крупная типографика** и полноэкранные фото/видео-фоны (в админке — нет, это рабочий инструмент). Добавить в токены секцию `typography.hero` (крупный заголовок, ~64-96px на десктопе) — не требуется в токенах админки, но нужна здесь.
- Тёмные секции (`WhyPhomiSection`, футер) используют `tokens.color.surface.menu` (`#333333`) как фон — то же значение, что фон SideMenu в админке, для консистентности бренда.
- Кнопки-CTA (`KONTAKTIRAJ NAS`, `KATALOG MATERIJALA`, `POGLEDAJ SVE PROJEKTE`) — по скриншотам это **outline-кнопки** (бирюзовая рамка, прозрачный/тёмный фон, бирюзовый текст), а не залитые — отдельный вариант `UButton` (`variant="outline"`, `color="brand"`), завести один раз в `app.config.js` под именем `variant: 'cta-outline'`, не описывать инлайн-классами в каждом месте использования.

## 6. Мультиязычность

### 6.1 Язык интерфейса

`@nuxtjs/i18n`, три локали — `sr` (дефолт), `en`, `ru`, файлы `i18n/locales/{sr,en,ru}.json`. Переключатель — в TopBar (п.4.1) и продублирован в мобильном overlay-меню.

**Важно для SEO публичного сайта (в отличие от админки, где это не требовалось):**
- Каждая локаль — на своём префиксе URL (`/en/katalog`, `/ru/katalog`, `sr` — без префикса как дефолтная, либо все три с префиксом — решить на этапе реализации и зафиксировать, т.к. от этого зависит `hreflang`-разметка).
- Обязательные `<link rel="alternate" hreflang="...">` на каждой странице для всех трёх локалей — через `useHead()`/встроенные хелперы `@nuxtjs/i18n` (`useLocaleHead()`), не вручную.
- `sitemap.xml` включает все локализованные варианты URL (модуль `@nuxtjs/sitemap`, если разрешён по стеку — уточнить при реализации, либо генерировать вручную в `server/routes/sitemap.xml.js`).

### 6.2 Локализованный контент

Два вида контента, как и в админке (п.5 админ-ТЗ), но с другим балансом:

1. **Контент сущностей из CRM** (`Product.name`, `Product.description`) — формат `{ values: { sr, en, ru } }`, отображается через `<LocalizedText>` — **тот же компонент**, что и в админке (переиспользуется из общего пакета, см. п.1.3), логика фолбэка идентична (текущий язык → `sr` → пусто).
2. **Контент самого сайта** (тексты секций главной, о компании, «стать дилером» и т.п.) — это **не** данные из CRM, у бэкенда таких сущностей нет. Хранится как обычные i18n-строки в `i18n/locales/{locale}.json` — редактируется через код/деплой, а не через админку CRM. **Уточнить с заказчиком**, не ожидается ли отдельная CMS-панель для редактирования этих текстов без разработчика — если да, это отдельная задача вне текущего ТЗ (потребуется, например, headless CMS или расширение админки новой сущностью `SiteContent`).

## 7. Формы («Стать дилером», «Контакт»)

### 7.1 Общий подход

Обе формы — простые, без BFF-прокси к тяжёлому CRM-флоу, если не оговорено иное:

- `POST /api/forms/dealer` и `POST /api/forms/contact` — Nuxt server routes.
- Валидация — Zod-схема (имя, телефон/email — минимум один из контактов обязателен, компания — опционально, сообщение).
- Действие на сервере: **уточнить с бизнесом одно из двух**:
  - (A) простая отправка email на `runtimeConfig.mail.contactRecipient` (транзакционный email-провайдер или SMTP) — быстрее в реализации, ничего не сохраняется в CRM автоматически;
  - (B) создание записи-лида в бэкенде (например, `Partner` со статусом «на рассмотрении» или отдельная сущность `Lead`, если бэкенд её поддерживает) — тогда заявки видны прямо в админке. Это требует изменений/уточнения на стороне бэкенда (сущности `Lead` в текущем бэкенд-ТЗ CRM нет — либо переиспользовать `Partner`, либо это отдельная бэкенд-задача, не покрытая текущим ТЗ).
- **Рекомендация [best practice]**: начать с варианта (A) для скорости запуска, заложить в код форм-хендлер так, чтобы переход на (B) был заменой одной функции (`submitDealerForm`), а не переписыванием формы.
- Rate-limiting на уровне Nuxt server route (простая in-memory защита от спама) — как в форме логина админки (п.4.5 админ-ТЗ).
- Honeypot-поле или капча (уточнить с заказчиком необходимость reCAPTCHA/Turnstile) — публичные формы без авторизации требуют базовой антиспам-защиты, которой не было в форме логина админки.
- После успешной отправки — toast/страница благодарности (`/postani-diler/hvala` или инлайн-состояние формы), не просто `alert`.

### 7.2 Форма «Стать дилером»

Поля (по референсным скриншотам — секция минималистична, поля уточнить с заказчиком при вёрстке, разумный дефолт):

```js
{
  companyName: z.string().min(1).max(200),
  contactName: z.string().min(1).max(200),
  phone: z.string().max(32),
  email: z.string().email(),
  city: z.string().max(200),        // город/регион дилера
  message: z.string().max(2000).optional(),
}
```

### 7.3 Форма «Контакт»

```js
{
  name: z.string().min(1).max(200),
  email: z.string().email(),
  phone: z.string().max(32).optional(),
  message: z.string().min(1).max(2000),
}
```

## 8. Каталог (`/katalog`)

### 8.1 Назначение

**Базовый** каталог (по требованию заказчика — не полноценный e-commerce): показать товары с картинкой, названием, ценой и статусом доступности, без оформления заказа/оплаты/личного кабинета. Цель — витрина + генерация заявок.

**[v1.1, отличие от исходного scope]** В отличие от изначального требования «без корзины», по факту реализации добавлена корзина (список интересующих товаров, собираемый посетителем перед отправкой одной заявки) — см. `useCart.js`/`CartDrawer.vue`. Это не корзина e-commerce (нет оформления заказа/оплаты), а способ собрать несколько товаров в одну заявку вместо кнопки «Узнать больше» на каждой карточке по отдельности.

### 8.2 Источник данных

`GET /api/catalog/products` (Nuxt server route) → на бэкенде `ProductsService.List` с фильтром `statuses: [ACTIVE]` (см. п.1.1), курсорная пагинация как в админке, но с более простым набором фильтров для публичного посетителя (см. п.8.5).

Ответ, отдаваемый браузеру, — урезанный до нужд карточки:

```json
{
  "items": [
    {
      "id": "uuid",
      "sku": "...",
      "name": { "sr": "...", "en": "...", "ru": "..." },
      "imageIds": ["uuid1", "uuid2"],
      "price": { "amount": 123456, "currency": "RSD" },
      "status": "PRODUCT_STATUS_ACTIVE"
    }
  ],
  "nextCursor": "..."
}
```

Изображения — через `<img :src="`/api/images/${imageIds[0]}`">`, тот же проксирующий passthrough-роут, что в п.4.6 админ-ТЗ (`GET /images/{id}` публичен и без токена, поэтому можно проксировать напрямую или отдавать прямой URL бэкенда — то же архитектурное решение, что и там; рекомендация — проксировать для скрытия адреса бэкенда).

### 8.3 Карточка товара

```vue
<!-- app/components/catalog/ProductCard.vue -->
<article class="rounded-lg border overflow-hidden">
  <NuxtImg :src="imageUrl" :alt="localizedName" loading="lazy" />
  <div class="p-4">
    <LocalizedText :value="product.name" tag="h3" />
    <MoneyLabel :amount="product.price.amount" :currency="product.price.currency" />
    <StatusBadge :status="product.status" :map="CATALOG_STATUS_MAP" />
  </div>
</article>
```

- `<LocalizedText>` / `<MoneyLabel>` / `<StatusBadge>` — **переиспользуются из общего пакета** с админкой (п.1.3), не переписываются заново.
- `CATALOG_STATUS_MAP` — упрощённая, публичная версия маппинга статусов (в отличие от `STATUS_COLOR_MAP.product` в админке, где статусов может быть больше — `Draft`, `Archived` и т.п. — публичный посетитель видит только бинарный смысл: **«Dostupno»** (зелёный, статус `Active`) / **«Nije dostupno»** (серый, любой другой не-`Active` статус — хотя таких карточек в списке в принципе не должно быть, т.к. фильтр на BFF уже отсекает non-active, см. п.8.2; этот маппинг — подстраховка на случай, если бэкенд в будущем введёт промежуточные статусы вроде «скоро в наличии»).
- Клик по карточке → `/katalog/[id]` (или `[sku]`, если решено использовать человекочитаемый URL вместо uuid — **рекомендация [best practice]**: использовать `sku` в URL, а не `id`, т.к. SKU по проекту неизменяем и читаем человеком, лучше для SEO, чем голый UUID).

### 8.4 Сетка — 4 колонки на больших экранах

Требование заказчика: **4 в ряд на десктопе**. Реализация — простая CSS-grid, без кастомного JS-выравнивания:

```css
.catalog-grid {
  display: grid;
  gap: 24px;
  grid-template-columns: repeat(1, minmax(0, 1fr));   /* < sm: 1 колонка */
}
@media (min-width: 640px)  { .catalog-grid { grid-template-columns: repeat(2, minmax(0, 1fr)); } } /* sm/md: 2 */
@media (min-width: 1024px) { .catalog-grid { grid-template-columns: repeat(3, minmax(0, 1fr)); } } /* lg: 3 */
@media (min-width: 1280px) { .catalog-grid { grid-template-columns: repeat(4, minmax(0, 1fr)); } } /* xl+: 4 — требование заказчика */
```

- На `lg` (1024-1279px) — 3 колонки, а не сразу 4 (иначе карточки станут слишком узкими для картинки+текста); на `xl`/`2xl` (≥1280px) — ровно 4, как просил заказчик. Финальные пороги согласовать при вёрстке по реальным макетам, значения выше — разумный дефолт **[best practice]**.
- Пагинация — «Загрузить ещё» (infinite scroll или кнопка) поверх курсорной пагинации из п.8.2, **не** классическая нумерация страниц — быстрее для мобильного UX и проще в реализации на курсорном API.

### 8.5 Фильтры (минимальный набор для базового каталога)

По требованию «каталог нужно сделать базовый» — **без** сложной панели фильтров, как в админке (п.9.1 админ-ТЗ). Минимум:

- Категория (`categoryIds`) — горизонтальные табы/чипы над сеткой (не выпадающий `<UMultiSelect>`, это не рабочий инструмент, а витрина).
- Поиск по названию — опционально, если заказчик подтвердит необходимость на этом этапе; при базовой реализации может быть отложен на следующий этап.
- Сортировка (по цене/новизне) — опционально, аналогично.

### 8.6 Детальная страница товара (`/katalog/[sku]`)

Базовая версия: галерея изображений (все `imageIds`, не только первое), `LocalizedText` для названия и описания, `MoneyLabel`, `StatusBadge`, характеристики товара (`Product.details` — key→LocalizedString, отображается простой таблицей/списком, тот же формат данных, что редактируется в админке через `keyValueLocalized`, здесь — только на чтение), кнопка CTA «Kontaktirajte nas povodom ovog proizvoda» → форма контакта (п.7.3) с предзаполненным полем сообщения (`Interesuje me: {sku} — {name}`).

SEO: `useSeoMeta()` на каждой карточке — `title`, `description` (из `Product.description`, урезано до ~160 символов), `og:image` (первое изображение товара).

## 10. Наблюдаемость и производительность

- **SSR + кэширование**: страницы каталога и главная — кандидаты на `nitro.routeRules` с `swr` (stale-while-revalidate, например 5 минут) вместо `ssr: true` на каждый запрос — каталог не меняется поминутно, а нагрузка от анонимных посетителей может быть выше, чем в админке.
- **Изображения**: `@nuxt/image` (`NuxtImg`) для автоматической генерации `srcset`/ленивой загрузки — критично для LCP на hero-изображении и в сетке каталога с 4 колонками фото.
- **Core Web Vitals**: hero-изображение — `preload`/`fetchpriority="high"`, остальные изображения — `loading="lazy"`.
- Ошибки клиента — тот же паттерн, что в п.13 админ-ТЗ (`vue:error` → `server/api/log/client-error.js`), но без привязки к `user id` (посетитель анонимен) — просто route + timestamp + user agent.
